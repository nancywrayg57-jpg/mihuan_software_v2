## 项目背景与复刻目标

蜜獾项目的首期目标是建设正式对外发布的多语言企业官网独立站，用于展示公司形象、产品能力、企业背景、资讯与招聘信息。官网必须在首页及关键页面显著说明：蜜獾公司是俄罗斯 `zennolab` 公司在中国的运营实体。

复刻目标不是逐字复制 `zennolab.com` 的内容、产品矩阵或品牌素材，而是借鉴其 B2B 软件官网的信息组织、页面节奏、视觉层级和转化路径，形成蜜獾自己的品牌表达。

已确认首期范围：

| 维度 | 结论 |
|---|---|
| 站点类型 | 正式对外发布的企业官网独立站 |
| 正式域名 | `https://www.honeybadgersoft.com/` |
| HTTPS | `Let's Encrypt` 证书，需支持自动续签 |
| 语言范围 | 中文、英文、俄语 |
| 一级页面 | 首页、产品介绍、新闻资讯、人才招聘、关于我们 |
| 公共能力 | 统一页头导航、统一页脚、面包屑、导航栏语言切换、全局客服悬浮按钮 |
| 内容维护 | 首期默认“结构化内容文件 + 配置化公共信息”，复杂 CMS 待确认且默认不进入首期 |
| 不做项 | 会员、支付、订单、库存、资金、复杂后台 CMS、纯前端伪数据后台 |

### 核心信息架构规律

- 参考站首页以产品矩阵和公共入口为核心；蜜獾当前应映射为“4 项常规产品/服务 + 跨境网络服务合并入口 + 咨询入口 + 新闻/招聘/关于我们入口”，不得继续以旧 ZennoLab 产品或拆分后的多项 IP 产品作为官网产品事实。
- 产品页可继续采用“首屏价值主张 -> 核心能力 -> 适用场景 -> 建设/使用/学习/陪跑流程 -> 交付支持 -> 咨询 CTA”的结构。
- 导航层保留首期 5 个一级页面：首页、产品介绍、新闻资讯、人才招聘、关于我们。产品详情作为产品介绍页下的二级内容，不扩张为一级导航。
- 多语言、`hreflang`、预渲染 SEO 和页面标题描述必须跟随“4 项常规产品/服务 + 跨境网络服务”同步更新；不能只更新中文页面而保留英文/俄文旧产品矩阵。
- 视觉层采用白色、浅蓝灰、亮蓝 CTA、产品强调色、圆角卡片和轻阴影，强调专业、克制、可信。

## 当前需求文档摘要

`docs/requirements_v2.md` 是当前唯一需求基线，`docs/蜜獾官网项目需求分析.md` 是在其基础上的开发级细化文档。

核心需求摘要：

- 官网是正式项目，不是 Demo 或临时展示页。
- 必须支持中文、英文、俄语三语浏览。
- 首期固定 5 个一级页面，不做无边界扩页。
- 全站公共层包括页头、页脚、语言切换、面包屑、客服悬浮按钮，必须优先设计和实现。

- 人才招聘需提供岗位展示和投递/联系路径。
- 对外邮箱使用阿里云企业邮箱。

- 客服入口当前以真实微信、QQ 和企业邮箱为已确认渠道；钉钉待配置且上线阻塞，禁止使用假入口。

## 整体系统架构

首期建议采用“静态/预渲染官网 + 结构化内容 + 集中配置 + 可选 API 演进层”的架构。

```text
访客浏览器
  -> 正式域名 https://www.honeybadgersoft.com/
  -> CDN / Nginx / 静态资源服务
  -> 预渲染页面或静态站点产物
  -> 结构化内容文件
  -> 公共配置 site_config
```

首期架构原则：

- 优先保证 SEO、三语、响应式和正式域名上线能力。
- 当前 `UI/` 静态官网实现不反向锁定最终前端框架；若后续新开工程仓或迁移现有页面，可评估 Next.js、Astro、Nuxt 或其他支持 SSG/SSR 的方案。
- 不建议首期引入复杂 CMS；新闻、招聘、产品、关于我们内容先使用结构化内容文件维护。
- 若后续确认需要 CMS 或表单能力，应作为 API 演进层设计，并以 `openapi.yaml` 作为前后端契约单点信任来源。
- 所有公共信息集中配置，包括域名、企业邮箱、客服渠道、ICP、版权、品牌关系说明、联系方式。

推荐逻辑分层：

| 层级 | 职责 |
|---|---|
| 展示层 | 页面路由、布局、响应式、可访问性、SEO 标记 |
| 公共组件层 | Header、Footer、Breadcrumb、LanguageSwitcher、FloatingSupport、CTA、FeatureCard、Badge |
| 内容访问层 | 读取结构化内容文件，按 locale、page、section、slug 获取内容 |
| 配置层 | 管理域名、邮箱、客服渠道、备案位、版权、品牌关系说明 |
| API 层 | 首期可不存在；如引入 CMS、表单或招聘投递，必须按 OpenAPI 契约实现 |
| 数据层 | 首期可为内容文件；如引入数据库，必须使用 migration、tenant/org 隔离与版本控制 |

## 前端架构分析

### 页面路由

建议将 5 个一级页面作为稳定路由基础：

| 页面 | 建议路由 | 说明 |
|---|---|---|
| 首页 | `/` 或 `/{locale}` | 首页不显示面包屑 |
| 产品介绍 | `/products` 或 `/{locale}/products` | 承载产品能力、场景价值、素材和咨询 CTA |
| 新闻资讯 | `/news` 或 `/{locale}/news` | 展示企业活动、行业新闻；详情页作为二级内容 |
| 人才招聘 | `/careers` 或 `/{locale}/careers` | 展示岗位列表、岗位详情和投递方式 |
| 关于我们 | `/about` 或 `/{locale}/about` | 重点说明企业背景、主体关系和联系方式 |

语言路由策略待真实框架确认后确定，但必须满足：

- 每个页面都有中文、英文、俄语真实内容。
- SEO metadata、`hreflang`、canonical、站点地图必须覆盖语言维度。
- 切换语言时应保持当前页面语义位置，例如 `/zh/products` 切到 `/en/products`，不能跳回首页。

### 公共组件

公共组件应先于具体页面开发：

| 组件 | 必备能力 |
|---|---|
| `SiteHeader` | 一级导航、语言切换、移动端菜单、当前路由高亮 |
| `Breadcrumb` | 除首页外统一显示，位于页头导航下方 |
| `SiteFooter` | 品牌说明、邮箱、客服入口、ICP、版权、支持外链预留 |
| `LanguageSwitcher` | 三语切换，使用真实 locale 内容 |
| `FloatingSupport` | 全站常驻，支持微信、QQ、钉钉真实入口 |
| `CTAButton` | 支持咨询、了解产品、获取资料、投递简历等明确目标 |
| `FeatureCard` | 产品能力、场景、新闻/招聘摘要卡片 |

### 视觉 token

视觉 token 以当前 `UI/assets/styles.css` 为准，并结合生产物料与页面文案转换为蜜獾品牌表达：

- 主交互蓝参考：`#418cf5` / `#377dff`
- 背景：白色、`#f7f8fa`、`#eef3ff`
- 字体：Open Sans、Inter，并补充中文字体 fallback，如 Noto Sans SC、Microsoft YaHei、PingFang SC
- 卡片：12px 左右圆角、24px 内边距、轻阴影
- 按钮：经典页面可使用 pill 风格，现代产品模块可使用 10px 圆角实按钮

注意：当前工作区未发现独立设计系统文件；不得把不存在的旧分析产物当作正式前端仓代码或当前设计基线。

### 前端实现约束

- 禁止动态拼接 Tailwind 类名，例如 `grid-cols-${count}`；动态布局使用内联 `style` 或 CSS 变量。
- 涉及编辑型 Dialog/Modal 时必须由外层传入 `key` 强制重挂载；首期官网若无编辑弹窗，此约束作为后续 CMS/API 演进约束。
- 日期不得直接把原生 `Date` 输出到 JSX/模板，必须使用统一格式化函数。
- 所有 API/fetch 调用必须检查 `response.ok`、`content-type`，并对 HTML 错误页或非 JSON 响应抛出包含 HTTP 状态码的错误。
- 不允许用纯前端 state 假装完成保存、批量重试、客服、语言切换或内容发布。

## 后端/API 架构分析

首期需求没有确认必须建设后端。默认建议：

- 官网前台内容使用结构化文件维护。
- 静态构建或预渲染产物直接部署。
- 客服入口使用真实外部链接、二维码或跳转协议，不伪造后端能力。
- 暂不建设会员、支付、订单、库存、资金、复杂 CMS。

若后续确认需要后端/API，API 范围应限制在真实业务需求内：

| API 能力 | 首期状态 | 设计要求 |
|---|---|---|
| 内容读取 API | 待确认 | 若引入 CMS，必须按 locale、page、section 查询，禁止前端伪造字段 |
| 新闻/招聘管理 API | 待确认，默认二期 | 必须有权限、状态机、版本号与审计字段 |
| 联系表单 API | 待确认 | 需防垃圾提交、速率限制、明确失败响应 |
| 客服渠道配置 API | 待确认 | 首期可使用配置文件；若接口化，必须保护后台修改权限 |
| 上传媒体 API | 待确认 | 需文件类型、大小、病毒扫描或安全策略 |

API 架构红线：

- `openapi.yaml` 是前后端接口契约单点信任来源。
- 前端只能使用基于 OpenAPI 生成或严格对齐的 client/types，不允许本地打补丁伪造 API。
- 所有 CRUD、查询、更新都必须携带 `tenant_id` 或 `org_id`；即使首期只有蜜獾一个站点，也要为后续多租户/多组织扩展保留隔离边界。
- 禁止仅凭主键更新或读取数据库记录。
- 数据库结构变更必须使用带时间戳的增量 migration，包括 `.up.sql` 与安全 `.down.sql`，禁止直接覆盖 `schema.sql`。

## 数据模型与领域对象分析

首期内容模型应围绕“页面 -> 模块 -> 字段 -> locale”组织。

### 核心领域对象

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `SiteConfig` | `org_id`、`domain`、`brand_name`、`relation_statement`、`email`、`icp_text`、`copyright_text` | 全站公共配置 |
| `Locale` | `code`、`label`、`is_default`、`enabled` | 中文、英文、俄语 |
| `NavigationItem` | `org_id`、`key`、`label`、`path`、`order`、`locale` | 一级导航与可选二级入口 |
| `PageSeo` | `org_id`、`page_key`、`locale`、`title`、`description`、`keywords`、`canonical_path` | 页面 SEO 元数据 |
| `HomeSection` | `org_id`、`section_key`、`locale`、`headline`、`body`、`media`、`cta` | 首页模块 |
| `Product` | `org_id`、`slug`、`locale`、`name`、`summary`、`features`、`scenarios`、`assets`、`cta` | 产品/服务能力 |
| `NewsArticle` | `org_id`、`slug`、`locale`、`category`、`title`、`summary`、`publish_date`、`cover`、`body`、`status` | 企业活动与行业新闻 |
| `JobPosting` | `org_id`、`job_id`、`locale`、`title`、`location`、`job_type`、`summary`、`responsibilities`、`requirements`、`apply_method`、`status` | 招聘岗位 |
| `SupportChannel` | `org_id`、`channel`、`display_name`、`entry_type`、`entry_value`、`enabled` | 微信、QQ、钉钉客服入口 |
| `MediaAsset` | `org_id`、`asset_id`、`alt`、`url`、`mime_type`、`width`、`height`、`locale` | 图片、截图、视觉素材 |

### 数值与精度

首期不建设支付、订单、库存、资金、计费或额度业务。如二期新增套餐、报价、余额、额度、库存等能力，必须使用高精度数值方案：

- Go 后端使用 decimal 类库，例如 `shopspring/decimal`。
- Node.js 使用 Decimal.js、Big.js 或数据库 decimal 类型映射。
- 禁止使用 Float/Double 或原生浮点算术处理金额、库存、计费、额度。

## 权限、租户与数据隔离设计

首期前台官网以公开只读访问为主，权限模型可保持简单，但架构上不能放弃隔离边界。

### 访问角色

| 角色 | 权限范围 |
|---|---|
| 访客 | 公开页面浏览、语言切换、点击客服/邮箱/外链 |
| 内容编辑 | 待 CMS 确认后才存在；可创建/编辑新闻、招聘、产品内容 |
| 审核/发布人员 | 待 CMS 确认后才存在；可审核、发布、下线内容 |
| 管理员 | 待 CMS 确认后才存在；管理站点配置、客服渠道、权限 |

### 隔离策略

- 所有可持久化数据必须带 `org_id` 或 `tenant_id`。
- 后端查询必须从认证上下文或站点上下文解析 `org_id`，并无条件加入 WHERE 条件。
- 更新和删除必须同时匹配业务主键与 `org_id`，禁止 `UPDATE table SET ... WHERE id = ?`。
- OpenAPI schema 中应显式表达组织隔离字段或由服务端上下文保证隔离，不允许前端绕过。
- 内容文件方案也建议保留逻辑组织字段，例如 `org_id: honeybadger`，避免后续迁移到 CMS 时丢失隔离语义。

## OpenAPI 契约设计策略

当前首期可无 API；一旦引入后端，必须遵循以下策略：

- `openapi.yaml` 是接口契约唯一事实源。
- 后端结构体注解或 API schema 生成 OpenAPI，前端从 OpenAPI 生成类型和 client。
- 字段缺失必须反向修改后端 schema 或注解，禁止前端本地模拟、补丁或硬编码兼容。
- 每个响应必须有明确 envelope 或错误结构，例如 `code`、`message`、`request_id`、`details`。
- 所有列表 API 必须定义分页、排序、过滤、locale、org/tenant 隔离语义。
- 非 JSON 响应、HTML 错误页、空 body 必须被 fetch wrapper 明确识别并抛错。

建议 API 分组：

| 分组 | 可能接口 |
|---|---|
| `SiteConfig` | 获取站点公共配置、客服渠道配置 |
| `Content` | 获取页面内容、产品、新闻、招聘 |
| `AdminContent` | 待 CMS 确认后提供创建、编辑、审核、发布、归档 |
| `Contact` | 待确认的联系表单或简历投递 |
| `Health` | 健康检查、版本信息 |

## 状态机与业务流程设计

复杂业务状态必须使用状态机，不允许在业务逻辑中硬编码 `status = 1`。

首期静态内容也建议按发布生命周期建模，方便未来迁移到 CMS：

```text
draft -> review -> approved -> scheduled -> published -> archived
                 -> rejected
```

适用对象：

- 新闻资讯：草稿、审核、定时发布、已发布、归档。
- 招聘岗位：草稿、审核、已发布、暂停招聘、已关闭、归档。
- 产品内容：草稿、审核、已发布、归档。
- 客服渠道配置：待配置、待验证、已启用、已停用。
- 部署发布：构建中、待验收、已发布、回滚中、已回滚。

状态机要求：

- 每次状态流转必须记录操作者、时间、原因和前后状态。
- 不允许跨越非法状态，例如草稿直接归档、已关闭岗位重新发布需经过审核。
- 状态枚举建议在应用层数据字典维护，数据库层不使用业务 ENUM；数据库字段使用 VARCHAR，并由应用层校验。

## 并发控制与数据一致性策略

首期内容文件方式的并发风险主要来自多人同时编辑内容和公共配置。建议：

- 内容文件由版本管理系统或内容仓库控制，合并前做 review。
- 三语内容矩阵应有 schema 校验，避免某语言字段缺失。
- 构建阶段校验所有路由、链接、图片、SEO metadata 和 locale 内容完整性。

若引入 CMS/API/数据库：

- 高频更新字段必须使用 `version` 乐观锁或 Redis 分布式锁。
- 内容、招聘、客服配置等后台编辑对象应带 `version` 字段，更新时使用 `WHERE id = ? AND org_id = ? AND version = ?`。
- 发布流程应使用事务，确保内容状态、发布记录、缓存刷新一致。
- 缓存 key 必须包含 `org_id` 与 `locale`。
- 金额、库存、计费、额度等能力当前不在首期；如后续新增，必须使用 decimal 高精度类型与数据库事务，禁止无锁内存计算。

## 错误处理与 API 响应防御策略

前端应建立统一请求封装，所有 fetch/API 调用必须满足：

1. 检查 `response.ok`。
2. 检查 `content-type` 是否为预期 JSON。
3. 对 HTML 错误页、空响应、非 JSON 响应抛出包含 HTTP 状态码、URL、请求 ID 的明确错误。
4. 解析错误响应体时限制长度，避免把整页 HTML 或敏感信息直接展示给用户。
5. 用户界面只展示可读错误，日志层保留完整诊断信息。

示例策略：

```ts
async function parseJsonResponse(response: Response) {
  const contentType = response.headers.get("content-type") ?? "";

  if (!response.ok) {
    throw new Error(`HTTP ${response.status} ${response.statusText}`);
  }

  if (!contentType.includes("application/json")) {
    throw new Error(`HTTP ${response.status}: expected JSON, got ${contentType || "unknown"}`);
  }

  return response.json();
}
```

对于首期静态站，仍需处理：

- 图片加载失败的 fallback。
- 外链跳转失败或钉钉客服配置缺失的上线阻断。
- 三语内容缺失时在构建阶段失败，不允许上线后才暴露空文案。
- 404 页面、500 静态托管错误页、Nginx fallback 策略。

## 后续开发建议

1. 先完成 S-1 范围冻结，确认 CMS 是否首期需要；未确认前默认结构化内容文件。
2. 输出三语内容矩阵，按页面、模块、字段、locale 管理正式文案。
